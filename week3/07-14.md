###### 2. 가장 막혔던 문제와 해결 과정
- 문제 상황 또는 증상: 이미지를 담은 요청이 왔을 때, 이를 어떻게 저장할지에 대한 고민.
- 처음 추측한 원인: DB에 BLOB으로 저장할지, 서버 디스크에 저장하는 것이 타당할지 고민되었음.
- 원인을 확인하기 위해 시도한 방법: AI·웹사이트 탐색으로 두 방식의 트레이드오프(용량·조회 성능·백업·서빙 방식)를 비교.
- 해결 방법: 서버 파일시스템에 저장하고 파일명은 UUID로 생성해 충돌을 방지했으며, DB에는 서빙 경로만 저장하고 기존 정적 서빙 구조를 재사용했다.

###### 3. 오늘 잘한 행동(개발과 관련된 것)
- 어떤 행동이었는지: QueryProfiler.measure를 도입해 나가는 모든 쿼리의 실행 시간을 로깅.
- 그 접근이 도움이 된 이유: N+1 문제 진단과 성능 파악이 가능했음.
- 다음에도 반복하고 싶은 점: 추측 대신 계측으로 병목을 먼저 확인하고, 성능 관련 코드는 로깅 off 시 비용이 0이 되도록 설계하는 습관.

###### 4. 오늘 아쉬웠던 행동(개발과 관련된 것)
- 비효율적이었던 접근/놓치거나 부족했던 점: 좋아요 기능에서 뒤늦게 갱신 유실(lost update) 문제를 발견함.
- 그렇게 된 원인: 좋아요를 엔티티 read-modify-write(SELECT 후 +1, 다시 UPDATE)로 구현해, 멀티스레드 동시 요청 상황을 처음부터 고려하지 못했다.
- 다음에는 다르게 해볼 구체적인 행동: 기능을 구현할 때 나가는 쿼리와 동시성(원자적 UPDATE 등)을 함께 검토하고, `SET x = x + 1` 같은 원자 연산을 기본으로 고려하겠다.
