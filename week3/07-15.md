###### 2. 오늘 가장 의미있었던 기술적 판단
- 내가 내린 판단: 조회 화면 렌더에 필요한 걸 DTO로 묶고 articles·users·comments를 한 번에 조인해서 가져오기로 했다. 네비게이션은 이 쿼리에 억지로 넣지 않고 이웃 id 쿼리로 따로 뺐다.
- 이유: 댓글마다 사용자를 다시 조회하던 N+1이 문제였고, 매 요청 전체 글을 메모리에 올려 정렬까지 하고 있어서 글이 늘수록 계속 무거워지는 구조였다.
- 고려했지만 안 쓴 대안: 윈도우 함수(LAG/LEAD)로 이웃까지 한 쿼리에 다 담기 → 결국 전체 스캔이 필요하고 SQL이 복잡해져서 뺐다. findAllOrdered는 두고 N+1만 없애는 방법도 있었지만 전체 findAll 문제가 그대로 남아서 제외.
- 영향: 쿼리 수가 댓글 수랑 무관하게 상수로 고정됐다. 컨트롤러에서 사용자 조회 로직이 사라지고 렌더 코드가 DTO만 읽으면 되니 훨씬 단순해졌다.

###### 3. 가장 막혔던 문제와 해결 과정
- 문제 상황: 좋아요를 빠르게 여러 번 누르면 카운트가 실제보다 적게 올라갈 수 있어 보였다.
- 처음 추측한 원인: read-modify-write라서 동시 요청이 같은 값을 읽고 각자 덮어쓰는 경합.
- 확인 방법: 서버가 스레드 풀(100)로 도는지, 커넥션이 스레드마다 따로인지 코드로 먼저 확인했고, 50스레드가 동시에 같은 글에 좋아요를 누르는 테스트를 만들어 재현했다.
- 실제 원인: findById → likeCount++ → save 세 단계 사이에 다른 요청이 끼어들어 증가분이 유실됨. 게다가 save가 like_count 말고 content·deleted_at까지 통째로 덮어쓰는 것도 발견.
- 해결: SET like_count = like_count + 1 원자 증가로 바꾸고 갱신값만 다시 조회하도록 분리.
- 다음에 먼저 확인할 것: 카운터·집계성 갱신은 "읽고 고쳐 다시 쓰는" 구조인지부터 보고, 그렇다면 DB 원자 연산으로 바꿀 수 있는지 검토.

###### 4. 오늘 잘한 행동(개발과 관련된 것)
- 어떤 행동: N+1 리팩터링을 DTO → 저장소 → 서비스 → 컨트롤러 순으로 쪼개서, 단계마다 컴파일·테스트 통과를 확인하고 넘어갔다. findAllOrdered 제거는 그걸 쓰던 컨트롤러를 바꾸는 스텝에서 같이 처리해 중간에 안 깨지게 했다.
- 도움이 된 이유: 어디서 깨졌는지 바로 알 수 있고 되돌릴 지점이 명확했다.
- 반복하고 싶은 점: 리팩터링 들어가기 전에 사용처를 먼저 grep으로 훑고 제거·교체 순서를 정하는 것.
