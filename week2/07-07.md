###### 2. 오늘 가장 의미있었던 기술적 판단
- 내가 내린 판단: Controller 계층을 도입하였고, 어떤 Controller에게 요청을 할당할 지는 RequestMapping에게 위임함.
- 그렇게 판단한 이유: 기존 RequestHandler에는 HTTP Method와 경로에 따른 처리를 if문으로 분기 처리하고 있었음. 추가적인 기능을 구현하기 위해서는 계속해서 if 문에서 요청을 분기처리해야 하는 문제가 있었음. => SRP 위배 + 가독성 최악
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향: RequestMapping을 통해 분기를 체계적으로 나눌 수 있었고, Controller 계층을 도입하여, 요청을 받고 응답을 반환하는 책임 부여하여 SRP 준수하도록 개선함. 테스트 용이.

###### 3. 가장 막혔던 문제와 해결 과정
- 문제 상황 또는 증상: getController() 메소드 구현 고민
- 처음 추측한 원인: 메서드와 경로를 비교하며, GET /create와 POST /create 를 분리해서 처리해야 했고, 어떤 과정으로 분기를 해야할 지 고민함. 
- 원인을 확인하기 위해 시도한 방법: Claude code와 대화 + 웹사이트 검색
- 해결 방법: (1) 메서드 + 경로가 정확히 매칭된 경우, (2) 경로는 옳지만 메서드는 옳지 않은 경우(405), (3) 미등록 경로는 정적 리소스를 찾아 응답하고 없다면 404 반환하도록 분기함.

###### 4. 오늘 잘한 행동(개발과 관련된 것)
- 어떤 행동이었는지: Step-5를 수행하기에 앞서, Database 코드를 살펴보니 User에 대한 영속성 코드만이 구현되어 있었고, 요구사항에 필요한 Session과 같은 클래스를 저장하는 데이터베이스를 구현하기 위해서는 중복되는 코드 및 네이밍에 모호한 부분이 있다고 생각함. Repository 계층 도입하기로 결정.
- 그 접근이 도움이 된 이유: 여러 데이터베이스를 만들더라도, 하나의 Database에 중복 코드(메서드)를 쌓을 필요 없음.
