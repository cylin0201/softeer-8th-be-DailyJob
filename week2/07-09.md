###### 2. 오늘 가장 의미있었던 기술적 판단
- 내가 내린 판단: IndexController, LogoutController에 SessionService 활용(service 계층 도입)
- 그렇게 판단한 이유: Session을 생성하고, 검증, 삭제하는 비즈니스 로직은 SessionRepository에서 충분히 가능하지만, 코드의 중복을 막고 테스트의 용이성을 높이기 위해 Controller, Repository 계층 중간의 비즈니스 로직을 담당하는 service 계층을 도입하기로 결정.
- 고려했지만 선택하지 않은 대안: 위의 컨트롤러에 SessionController나 SessionRepository를 의존하도록 할 수는 있었겠으나, Controller와 Repository 계층이 가지는 책임 범위를 넘어서는 것으로 판단하였음. 
- 이 판단이 코드 품질/테스트/유지보수에 미친 영향: Session 관련 비즈니스 로직의 테스트를 용이하게 할 수 있음. 실제로 세션이나 쿠키를 활용하는 로직에서 매번 SessionRepository를 의존하여 중복되는 코드를 활용하는 것보다도 이점이 있다고 봄.

###### 3. 가장 막혔던 문제와 해결 과정

- 문제 상황 또는 증상: 비로그인 상태에서 로그인 버튼을 누르면 405 Method Not Allowed가 발생함
- 처음 추측한 원인: 로그인 페이지의 정적 파일 경로(href)가 잘못됐다고 생각함
- 원인을 확인하기 위해 시도한 방법: RequestMapping에 등록된 라우트와 실제 요청 경로를 대조하고, 정적 페이지들의 href를 grep으로 확인함
- 실제 원인: GET /login이 POST /login과 경로가 겹쳐, "경로는 등록됐으나 메서드가 다름"으로 판정되어 정적 폴백으로 가지 못하고 405를 반환한 것이었음
- 해결 방법: GET /login을 정적 컨트롤러로 명시 등록하여 폼 보기(GET)와 로그인 처리(POST)를 분리함
- 다음에 비슷한 문제가 생기면 먼저 확인할 것: 405가 뜨면 경로 자체는 존재하는데 해당 메서드 매핑만 없는지, 라우팅 우선순위부터 확인할 것
